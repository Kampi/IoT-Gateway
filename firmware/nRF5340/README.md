## About

Firmware for the Nordic nRF5340 that acts as the OpenThread Radio
Co-Processor (RCP) for the gateway's Thread Border Router. It runs
Nordic's `ot_coprocessor` sample from the nRF Connect SDK on the nRF5340's
network core, and talks Spinel over HDLC-over-UART to `otbr-agent` on the
Verdin (`/dev/thread`, UART_4 - see
[os/layers/meta-iot-gateway-os/README.md](../../os/layers/meta-iot-gateway-os/README.md),
sections "Thread - nRF5340 RCP (UART_4)" and "SODIMM Pin Mapping").

This directory sets up a self-contained [west](https://docs.zephyrproject.org/latest/develop/west/index.html)
workspace so the sample can be fetched and built with two commands, without
vendoring the (multi-GB) nRF Connect SDK into git.

## Directory Breakdown

- **`Makefile`**: `setup` / `build` / `flash` / `dfu` wrappers around `west`
- **`app/west.yml`**: west manifest, pins the nRF Connect SDK version
- **`app/prj.conf`**: extra Kconfig layered on the sample's own `prj.conf`
- **`app/sysbuild.conf`**: sysbuild config, enables + configures the MCUboot child image
- **`app/mcuboot.conf`**: MCUboot Kconfig (serial recovery, entrance pin, signature type)
- **`app/boards/nrf5340dk_nrf5340_cpunet.overlay`**: `zephyr,ot-uart` chosen node - named
  after `BOARD` per Zephyr's own board-qualifier overlay convention
- **`app/boards/gateway.overlay`**: custom carrier board, TODO pins (see file)
- **`app/boards/mcuboot-nrf5340dk_nrf5340_cpunet.overlay`**: MCUboot recovery pin (P1.15,
  overriding the DK's own default Button 1) - see "DFU / Bootloader"
- **`app/boards/mcuboot-gateway.overlay`**: same recovery pin (P1.15) for the carrier
- **`app/boards/partitions.overlay`**: single-slot MCUboot partition table (see
  "DFU / Bootloader"), applied to both the app and MCUboot images
- **`app/dfu_signing_key.pem`**: DFU signing key, generated by `make dfu-keygen`, git-ignored
- **`app/heartbeat_led/`**: out-of-tree Zephyr module, blinks LED 1 for
  `TARGET=dk` builds - see "Heartbeat LED"
- **`toolchain.mk`**: machine-local toolchain environment, git-ignored (see "Toolchain")
- **`toolchain.mk.example`**: template for the above
- **`zephyr`, `nrf`, `modules`, ...**: fetched by `make setup`, git-ignored
- **`build`**: net-core (RCP + MCUboot) build output, git-ignored
- **`build_appcore`**: app-core companion build output, `TARGET=dk` only, git-ignored

Only `Makefile`, `README.md`, `.gitignore`, `toolchain.mk.example` and `app`
are tracked in git. Everything else is fetched on demand and reproducible
from `app/west.yml`, or is machine-local (`toolchain.mk`).

## Prerequisites

- Python 3 + `pip3`, and the `west` tool (`pip3 install west`)
- The Nordic/Zephyr toolchain (Zephyr SDK, i.e. `arm-zephyr-eabi-gcc`) - see
  [Nordic's install guide](https://docs.nordicsemi.com/bundle/ncs-latest/page/nrf/installation/install_ncs.html)
  if you don't already have the nRF Connect SDK toolchain installed (e.g.
  via nRF Connect for Desktop / VS Code)
- `nrfjprog`/`nrfutil` + a J-Link (on-board debugger on the nRF5340-DK) for
  `make flash`
- [`mcumgr`](https://github.com/apache/mynewt-mcumgr-cli) CLI for `make dfu`
  (image updates over UART, no SWD needed after the first flash)

## Toolchain

nRF Connect SDK's own CMake boilerplate auto-detects any NCS Toolchain
Manager install registered in the CMake user package registry
(`~/.cmake/packages/NcsToolchain`) and forces every sysbuild child image
(app + MCUboot) to use it - overriding `ZEPHYR_SDK_INSTALL_DIR` /
`ZEPHYR_TOOLCHAIN_VARIANT` set any other way. If that toolchain's own
bundled Python can't find its shared library at runtime (missing
`LD_LIBRARY_PATH` - can happen if it was never launched through the
nRF Connect VS Code extension / Toolchain Manager GUI, which normally
sets this up), every `make build` fails with something like:

```text
CMake Error ... Could NOT find Python3 (missing: Interpreter)
Reason given by package:
    Interpreter: Cannot run the interpreter ".../usr/local/bin/python3"
```

If you hit this: copy `toolchain.mk.example` to `toolchain.mk` (git-ignored)
and fill in your toolchain's path - the Makefile loads it automatically via
`-include toolchain.mk`. See the comments in that file for how to find the
right path and why it's needed.

If your toolchain works out of the box (e.g. a plain Zephyr SDK install,
no NCS Toolchain Manager registered), you don't need `toolchain.mk` at all.

**Always use `make <target>` (`make build`, `make flash`, `make dfu`, ...),
never a bare `west` command in your shell.** `toolchain.mk` is loaded by
`-include` inside the Makefile, so it only takes effect for the duration of
a `make` invocation - it is Makefile syntax (`export VAR := value`), not
valid shell, so you also can't just `source` it into your terminal. Running
`west flash` directly will fail with something like
`/usr/bin/env: 'python3.12': No such file or directory` because none of
`toolchain.mk`'s `PATH`/`LD_LIBRARY_PATH` made it into your shell.

`make flash` uses the `nrfjprog` west runner, which is a **separate**
system-wide install (the `nrf-command-line-tools` .deb from Nordic,
typically under `/opt/nrf-command-line-tools/bin`) - not part of the NCS
toolchain directory at all. If `make flash` fails with
`required program nrfjprog not found`, find it with
`dpkg -L nrf-command-line-tools | grep bin/nrfjprog` and add that directory
to `NRF_CMD_TOOLS_BIN` in your `toolchain.mk`.

If `make flash` fails with a JLink `HALT`/`erase` error (e.g. "The read
access failed" / "Halt returned error 1"), the board is usually just
stuck from an interrupted previous flash, not a real fault. Run
`make recover` (wraps `nrfjprog --recover`, add `NRFJPROG_SNR=<serial>` if
more than one board is connected), then retry `make flash`. If it also
fails, unplug/replug the DK's USB - especially likely if you're flashing
through USB passthrough into a VM, which is prone to this.

## Setup

```bash
cd firmware/nRF5340

# One-time: fetch the nRF Connect SDK / Zephyr workspace
make setup
```

This runs `west init -l app`, then `west update` to pull the nRF Connect
SDK (pinned in `app/west.yml`) plus Zephyr and all required modules as
siblings of `app`, and installs their Python requirements. This is a
multi-GB download and only needs to be repeated after bumping the
`revision` in `app/west.yml`.

## Building

```bash
# Stock nRF5340-DK (default) - safe to try immediately after `make setup`
make build
make flash
```

Once the carrier board's schematic is final and `app/boards/gateway.overlay`
has been updated with the real UART pins:

```bash
make build TARGET=gateway
make flash
```

`BOARD` and `TARGET` can be overridden independently, e.g.
`make build BOARD=nrf5340dk/nrf5340/cpunet TARGET=gateway` to test the
carrier's pin overlay while still using the DK's SoC-level board config -
there is no formal Zephyr board port for the carrier yet, since only the
UART pin routing differs from the DK.

Other targets: `make menuconfig`, `make clean` (removes `build` only),
`make pristine` (also removes the fetched west workspace).

Every build now produces two images via sysbuild: MCUboot and the signed
RCP application. `make flash` (SWD) writes both. See the next section for
updating just the RCP application afterwards, without SWD.

For `TARGET=dk`, `make build`/`make flash` additionally build and flash a
third, separate image to the **application core**
(`nrf/samples/nrf5340/empty_app_core`, into `build_appcore/`) - see
"Heartbeat LED" below for why this is needed.

## Heartbeat LED

For `TARGET=dk` only, an out-of-tree module
([app/heartbeat_led](app/heartbeat_led)) toggles the devicetree `led0`
alias (LED 1 on the DK silkscreen) once per second, as a simple visual
sign that the net-core firmware is running. It's wired in via
`ZEPHYR_EXTRA_MODULES` and enabled through
`app/boards/nrf5340dk_nrf5340_cpunet.conf`
(`CONFIG_APP_HEARTBEAT_LED=y`) - not touching the vendored
`nrf/samples/openthread/coprocessor` sources.

**This alone is not enough for the LED to actually blink.** The nRF5340's
network core owns no GPIO pins by default - every pin must be explicitly
forwarded to it by the application core
(`zephyr/dts/bindings/gpio/nordic,nrf-gpio-forwarder.yaml`). The DK's own
app-core devicetree
(`zephyr/boards/nordic/nrf5340dk/nrf5340_cpuapp_common.dtsi`) only
forwards the 4 Spinel UART pins by default, not LED0. Without app-core
firmware that forwards the rest, `gpio_pin_toggle_dt()` on the net core
silently does nothing.

That's what the `build_appcore`/app-core companion image from the
previous section is for: Nordic's `empty_app_core` sample forwards *all*
GPIO pins to the net core, then suspends the application core
permanently. `make build TARGET=dk` and `make flash TARGET=dk` build and
flash it automatically alongside the net-core image - no separate step
needed.

This also means any devicetree GPIO the net-core firmware uses (not just
the heartbeat LED - e.g. `mcuboot-button0` at P1.15, see "DFU /
Bootloader") only works once this app-core companion has been flashed at
least once. It's a one-time flash - `empty_app_core` doesn't need
re-flashing on every net-core update, only after an app-core erase or a
DK that never had it programmed.

## DFU / Bootloader

The RCP application is chain-loaded by [MCUboot](https://docs.mcuboot.com/),
so it can be swapped later over the same UART used for Spinel, without SWD
access. This is Option A from the design discussion: bootloader on the net
core only, no app-core/RPMsg involved.

```bash
# One-off: generate the signing key (also runs automatically on `make build`)
make dfu-keygen
```

`make dfu-keygen` writes `app/dfu_signing_key.pem` if it doesn't exist yet.
**Back this file up somewhere outside of git** - it is git-ignored on
purpose, and losing it means devices already in the field can no longer be
updated with a matching signature.

```bash
# Build (also signs the image with app/dfu_signing_key.pem)
make build

# First-ever flash still goes over SWD (writes MCUboot + the signed app)
make flash

# Later updates: hold the recovery pin (mcuboot-button0) low, reset the
# board, then upload the new signed image over UART
make dfu DFU_PORT=/dev/ttyACM0
```

`mcuboot-button0` is P1.15 on both targets (`app/boards/mcuboot-nrf5340dk_nrf5340_cpunet.overlay`
/ `mcuboot-gateway.overlay`), overriding the DK's own default (Button 1)
so the same physical wiring/behavior can be tested on the DK before the
carrier board exists - wire a button/jumper from P1.15 to GND on the DK
to enter recovery.

### Single-slot mode, not two-slot A/B

MCUboot is configured for **single-slot mode**
(`SB_CONFIG_MCUBOOT_MODE_SINGLE_APP=y` in `app/sysbuild.conf` - this is
the authoritative switch; it also propagates the matching
`CONFIG_MCUBOOT_BOOTLOADER_MODE_SINGLE_APP` to the app image and
`CONFIG_SINGLE_APPLICATION_SLOT` to MCUboot, both silently overridden if
set directly instead), not classic two-slot A/B swap or overwrite-only.
This was forced by measurement, not preference:

- The RCP application alone is **~135 KiB** built (`arm-zephyr-eabi-size`
  on `zephyr.elf`: `text=136864 + data=1299`), ~139 KiB once signed with
  the MCUboot header/trailer.
- Two slots big enough to hold that (~278 KiB) do not fit in the net
  core's 256 KiB flash at any partition split - two-slot DFU (swap *or*
  overwrite-only) was not an option regardless of tuning.

`app/boards/partitions.overlay` replaces the board's default four-way
split (`mcuboot` + `image-0` + `image-1` + `storage`, image-0/1 at ~92 KiB
each) with a three-way one sized for single-slot use, applied to both the
app and MCUboot images (they must agree on the same flash layout):

| Partition | Offset | Size | Measured usage |
| --- | --- | --- | --- |
| `mcuboot` | `0x00000` | 48 KiB | 41.6 KiB (84.6%) |
| `image-0` (app) | `0x0c000` | 184 KiB | ~135 KiB (~73%) |
| `storage` | `0x3a000` | 24 KiB | - (OpenThread dataset persistence) |

In single-slot mode, serial recovery writes a new signed image directly
into `image-0` - there is no secondary slot to stage it in first. The
trade-off: unlike two-slot swap, a bad or interrupted upload is not
automatically rolled back. MCUboot itself lives in its own separate
partition though, so serial recovery always stays reachable - a bad
`image-0` is corrected by holding `mcuboot-button0` and uploading a good
image again via `make dfu`, not by re-flashing over SWD.

The signing key type is ed25519 throughout (`make dfu-keygen`,
`app/sysbuild.conf`'s `SB_CONFIG_BOOT_SIGNATURE_TYPE_ED25519`,
`app/mcuboot.conf`'s `CONFIG_BOOT_SIGNATURE_TYPE_ED25519`) - the sysbuild
default is RSA-2048, which expects a different key file/format.

## Notes

- The sample is built for `nrf5340dk/nrf5340/cpunet` - the network core,
  which owns the 802.15.4 radio and its own UART peripheral. The app core
  is left unprogrammed; it is not needed for an RCP-only image.
- `app/prj.conf` intentionally leaves UART instance/baud/flow-control to the
  devicetree overlay (`app/boards/*.overlay`), since the coprocessor sample
  selects its Spinel UART via a devicetree `chosen` node rather than
  Kconfig. That `chosen { zephyr,ot-uart = &uart0; }` node has to be set
  explicitly for `nrf5340dk/nrf5340/cpunet` - Nordic ships a board overlay
  setting it for nRF52-series boards and nRF54L15 (see
  `nrf/samples/openthread/coprocessor/boards/`), but not for nRF5340; both
  `app/boards/nrf5340dk_nrf5340_cpunet.overlay` and `gateway.overlay` add it.
- The gateway's `uart4` devicetree node is currently `status = "disabled"`
  in `os/layers/meta-iot-gateway-os/recipes-kernel/linux/linux-toradex/iot-gateway-imx8mm.dts`
  (reserved for the Cortex-M4 core) - it must be enabled there before the
  RCP link can actually be used end-to-end.
